Design proposal · Upload MVP

Credit card statement ingestion

Turn a password-protected statement into reviewed transaction matches, reward entries, and correctly linked taxes and fees.

Core decision: stage statement rows before changing the ledger. Match existing transactions, review uncertain results, and apply approved changes once.

Created 5 October 2026 · Repository: Pennywise · Branch: wip/jev-integration
Proposed design; the schema, routes, and statement processing described here are not implemented.

01 · MVP scope

The user uploads a credit card PDF and supplies its password when needed. Pennywise extracts transactions, finds existing ledger entries, proposes missing entries, records rewards, and links separately billed charges to their underlying transaction where the statement supports that relationship.

  • Start with one issuer and a representative statement layout.
  • Support purchases, refunds, payments, separately billed taxes, fees, and interest as distinct row types.
  • Require an explicit review and apply action before changing financial data.
  • Keep unmatched and ambiguous rows visible, editable, and explainable.
  • Preserve source evidence and prevent duplicates across retries and re-uploads.

Automatic Gmail discovery, additional bank formats, reward eligibility calculations, and tax filing/export workflows are later work. “Taxes” here means charges shown on the card statement, such as GST on a fee.

02 · Import experience

  1. UploadSelect the card account and provide a PDF.
  2. UnlockPrompt for a password only when the PDF requires one.
  3. ExtractRead statement metadata, rows, rewards, and totals.
  4. MatchFind candidates in the selected account’s ledger.
  5. ReviewConfirm matches, new entries, charge links, and points.
  6. ApplyCommit approved changes and display their outcome.

The review screen shows each source row beside its proposed action: match, create, or ignore. It includes the chosen transaction, alternative candidates, rewards, related charges, and the PDF page/row evidence.

Show extracted totals and discrepancies before approval. A failed integrity check blocks application until extraction is corrected or a documented, explicit override is recorded. A reviewed row may remain unlinked when its relationship is unknown.

04 · Proposed data model

Keep source observations separate from ledger identity. A statement is evidence about transactions, not another ledger.

RecordKey fields and purpose
credit_card_statementsID, budget/account IDs, source, issuer, masked card suffix, period, statement date, currency, file hash/blob reference, opening/closing balance, due amount/date, status, parser version, review revision, error code.
credit_card_statement_rowsStatement ID, stable source row key, page/row position, raw description, transaction/posting dates, signed amount, currency, foreign amount/currency if present, bank reference, row type, extraction confidence, extracted reward fields.
statement_row_matchesSource row, candidate/selected transaction ID, proposed action, matching reason/confidence, reviewer decision, parent-charge proposal, and applied result. Persist review state separately from raw extraction.
reward_entriesBudget/account/program IDs, statement/source-row IDs, optional transaction ID, entry kind, signed points, observation date, source key, and provenance.
transactions additionsNullable parent_transaction_id and relationship_type for related tax, fee, and interest entries. Existing rows remain valid.

Use decimal amounts or integer minor units during extraction and matching. The existing SQL ledger uses NUMERIC(12,2) while the Go transaction model uses float64; compare canonical minor-unit amounts rather than raw floating-point equality.

Bank references are evidence, not assumed globally unique IDs. Scope all references and lookups to the budget and selected account. Preserve both transaction and posting dates; do not overwrite an existing transaction’s date solely because the statement uses posting dates.

A row match is unique per source row when applied. A transaction may have observations in multiple statements, but cannot satisfy multiple distinct purchase rows in the same statement. Legitimate grouped rows require explicit modeling and review.

05 · Deterministic reconciliation

  1. Validate account/card identity and statement period before searching the ledger.
  2. Find candidates in the same budget/account with compatible amount, currency, direction, and row type.
  3. Use a verified bank reference when available; otherwise rank by transaction/posting date proximity and normalized merchant evidence.
  4. Resolve candidates across the whole statement so two rows cannot independently claim the same transaction.
  5. Propose a unique strong match; leave ties and weak evidence for manual review.
  6. Propose creating missing transactions, preserving statement provenance and using the existing transaction service for ledger side effects.

The date window and confidence thresholds are configurable and must be calibrated against real statement fixtures. Repeated purchases of the same amount, foreign currency settlements, reversals, and existing entries that already include fees require review.

Payments may match existing transfer transactions. Never create a card-only payment entry automatically when doing so would duplicate or break an existing transfer pair. Opening balance, closing balance, and total due are summary fields, not transaction rows.

LLMs may extract fields or normalize descriptions. Application code owns identity decisions, amount checks, candidate allocation, and duplicate prevention. Existing categories, notes, and user corrections are preserved by default.

06 · Taxes, fees, and parent transactions

Use separate ledger entries for amounts the bank bills separately. Their relationship controls grouping, while their own amount controls accounting.

Foreign purchase                      ₹10,000
  Foreign currency markup                ₹350  [fee → purchase]
    GST on markup                         ₹63  [tax → fee]

Displayed group cost:                 ₹10,413
Ledger entries: three; each counted exactly once.
  • Tax included in the purchase amount is a breakdown only; adding it as an expense would double-count it.
  • Separately charged tax is matched or created as its own ledger entry and linked to the stated fee or purchase.
  • A monthly aggregate tax or fee remains standalone when no individual relationship is established.
  • Do not infer a parent solely from adjacent PDF rows. Use explicit descriptions/references and review uncertain links.
  • Both ends must share budget/account, be active, and be distinct. Relationship type is required exactly when a parent exists.
  • Prevent cycles. Support shallow nesting, including tax on a fee, and bound traversal depth.
  • Deleting a parent must not silently delete financial children. Require an explicit detach or reviewed group action.

Reports continue summing the individual entries. A displayed group total is derived and must never be added as an extra expense. Preserve each charge’s own date/category; a group spanning dates is not a substitute for period-based ledger reporting.

For the MVP, keep charges affecting multiple purchases unlinked. A future allocation table can represent many-to-many attribution without duplicating their monetary amounts.

07 · Reward points as a separate ledger

Store signed reward entries for earned points, bonuses, reversals, redemptions, expiry, and adjustments when the statement provides them. They do not change monetary balances.

  • Link points to a purchase only when the statement provides that attribution.
  • Store a monthly earned-points total at statement level when purchase-level detail is absent.
  • Keep “unknown” distinct from an explicitly reported zero.
  • Store opening/closing points balances as snapshots; they are not additional earned entries.
  • Do not add a summary earned total on top of its detailed earned entries. Use the total to validate the detail.
  • Deduplicate reward observations across repeated/overlapping imports. Preserve source keys and reversal relationships.

Show transaction points by aggregating linked entries. Programs remain separate, and monetary value is not inferred from points. Cashback actually credited to the card is a monetary transaction and must be matched independently.

08 · Protected PDFs and extraction artifacts

  1. Validate file signature and enforce upload, page-count, decompressed-size, and processing-time limits.
  2. If encrypted, return a password-required state. A wrong password leaves the statement retryable.
  3. Unlock in the API process with a PDF library or bounded subprocess. Keep the password in request memory and out of command-line arguments, persisted records, telemetry, and workflow inputs.
  4. Prefer extracting text during unlock and persisting only the artifact needed by the worker. If OCR needs unlocked page images/PDF bytes, store them with restricted access and a defined TTL.
  5. Pass statement ID and artifact reference into Temporal. Retry extraction from that artifact; once it expires, request unlock again.
  6. Clean up unlocked artifacts on success, cancellation, failure, and TTL expiry. Retain the original encrypted upload according to the chosen statement retention policy.

Try native PDF text first. Preserve page boundaries and table structure; use OCR/vision for scanned pages or unreliable text. Validate the structured result against a schema and statement arithmetic before generating review proposals.

If an external extraction provider receives statement text or images, disclose that in the upload flow and follow the configured provider policy. Passwords are never sent to an extraction model.

09 · Idempotency, consistency, and recovery

File hash detection handles identical uploads within a budget/account. Also check issuer/card/period identity because the same statement may be downloaded as different PDF bytes. Flag likely duplicate statements for review instead of treating different hashes as proof of different financial events.

Assign stable source row keys from the persisted extraction. Preserve legitimate identical purchases with separate occurrences; a hash of date/description/amount alone must not collapse them. Parser reruns create a versioned proposal and cannot silently change applied row identities.

Applying a reviewed statement locks its record, verifies the expected review revision, rechecks selected transactions and uniqueness constraints, and writes transaction changes, links, rewards, and application status in one database transaction.

  • Refactor or extend the transaction service to share the same database transaction for its balance, transfer, and correction side effects. Calling independently committed CRUD operations in a loop is not atomic.
  • Retries of an applied statement return its recorded result. Unique row application/reward source constraints provide a second line of defense.
  • Concurrent Gmail/manual creates are rechecked during apply. Ambiguity produces a conflict requiring renewed review.
  • Record created IDs and changed fields for audit. Future undo needs conflict-aware compensation; it is not a blind delete or balance reversal.
  • Notify clients after commit through existing websocket infrastructure.
uploaded → needs_password → queued → processing → review_ready → applied
                ↑                 ↓
          unlock retry         failed → retry

Cancellation is allowed before application.
An applied statement is immutable as an import result.

An unencrypted upload moves directly to queued after artifact preparation. Extraction validates printed debit/credit totals, balance arithmetic when the issuer’s format permits it, and points totals. Missing components or unexplained differences remain visible and block silent application.

Use existing auth and budget middleware. Verify account ownership, statement ownership, candidate transaction scope, and parent scope independently. Source file access must also be budget-scoped.

11 · Delivery plan and acceptance checks

  1. Establish the format: inspect a representative issuer statement; collect redacted fixtures including taxes, rewards, refunds, and card payments.
  2. Upload and unlock: statement records, storage reuse, protected-PDF handling, bounded extraction, and artifact cleanup.
  3. Extraction and review: structured rows, provenance, arithmetic validation, deterministic candidate matching, and editable review screen.
  4. Ledger enrichment: parent relationships, reward entries, atomic application, idempotency, and grouped display.
  5. Extend intake: Android upload, additional issuers, and Gmail statement discovery using the same pipeline.

Required validation before shipping

  • Encrypted and unencrypted PDFs work; incorrect passwords are recoverable and never appear in logs or workflow history.
  • Duplicate upload, workflow retry, and apply retry leave balances and points unchanged after the first successful application.
  • Identical repeated purchases remain separate; ambiguous matches and concurrent transaction changes require review.
  • Matched transactions retain user categories/notes, and no two distinct rows claim the same purchase.
  • Taxes included in an amount are not added again; separate charges affect balances once, including nested tax-on-fee cases.
  • Payments do not duplicate transfers; statement summary lines never become ledger transactions.
  • Monthly rewards and transaction rewards are not double-counted; unknown points are preserved.
  • Cross-budget/account matches and parent links fail; cycles fail; parent deletion cannot silently remove charges.
  • A failure midway through application rolls back transactions, side effects, reward entries, and import status together.
  • Totals mismatches are surfaced, and cancellation/expiry removes decrypted artifacts.

Use Go service/repository/workflow tests for these invariants and a manual browser check of upload, password retry, review, and apply. Introduce meaningful frontend integration coverage if a harness is established during implementation.

12 · Decisions still needed

  • First issuer/card and a representative statement: does it show points per transaction, monthly totals, or both?
  • Which taxes/fees are shown, and what references connect them to a purchase or fee?
  • PDF decryption/extraction library and OCR provider, validated against the chosen issuer’s protected files.
  • Original-file retention and temporary artifact TTL/storage protection.
  • Default categories for unmatched fees/taxes/interest and review behavior for payments/transfers.
  • Date tolerance, matching thresholds, and the precise rules for integrity-check overrides.

The first implementation milestone should be a correct, inspectable extraction of one protected statement. Use that evidence to finalize parser fields and matching rules before enabling ledger writes.
