# AGENTS.md — react-frontend

React 19 + Vite + Redux Toolkit web client for Pennywise.

## Commands
- `npm run dev` — Vite dev server
- `npm run build` — `tsc -b && vite build` (type-check is the test gate)
- `npm run lint` — ESLint (clean; keep it that way)
- `npm run preview` — serve the build
- `npm run test:e2e` — Playwright (`e2e/`) against a running demo stack with the real API and PostgreSQL; from the repo root `make smoke` starts a disposable one, runs it and tears it down. There are no unit tests.

## Layout
- `src/app/` — `store.ts` (root reducer, wires `apiClient` to the session, saves the session), `App.tsx` (router), `hooks.ts`, `middlewares.ts` (the listener that loads budget data when the budget or month changes)
- `src/features/<name>/` — `components/`, `hooks/`, `store/`, `types/` (+ `goals/` in category). A feature's page lives in it too (the dashboard page is `features/dashboard/components/Dashboard`).
- `src/components/common/` — widgets with no feature data: `Modal`, `Popover`, `Card` (+ `Segmented`), `Amount`, `Skeleton`, `PennywiseMark` (the icon, still or playing its loop; same keyframes as android's `PennywiseMark` and `docs/logo/pennywise-icon-animated.svg`, so change them together), `AppLoader` (the animated mark, for waits with nothing to draw yet), `ToastHost`, `pickers/`
- `src/components/layout/` — `Layout` (header bar, side panel, AgentChat), `Navbar`, `slots.ts` (`useHeader` / `useSidePanel`, how a page fills the header bar and side panel)
- `src/components/theme/` — `ThemeProvider`, `ThemeToggle`
- `src/utils/` — `api.ts` (`apiClient`), `format.ts` (every money, count, points and file-size format), `date.utils.ts`, `errorText.ts`, `toast.utils.ts`; `src/config/env.ts` — every `import.meta.env` read
- `src/styles/` — `index.css` (`@import '@heroui/styles'`, which brings Tailwind v4), `theme.css` (app palette; `--brand-deep`/`--brand`/`--brand-soft` are the accent blues in both themes and match the icon (`public/logo-mark.svg`: sky `--brand`, lines `--brand-soft`), so change the theme and `docs/logo` together; text on an accent background uses `--on-accent`; also maps HeroUI v3's tokens such as `--overlay`, `--surface`, `--border` onto it)

## Conventions
- Redux Toolkit slices per feature in `features/*/store/`, wired in `src/app/store.ts`.
- Use `useAppDispatch` / `useAppSelector` from `src/app/hooks.ts`, not the raw react-redux hooks.
- `apiClient` (`src/utils/api.ts`) injects `Authorization` and `x-budget-id` from the session `app/store.ts` gives it (`apiClient.connect`); `utils/` imports nothing from the store or features. Don't pass the budget id by hand. Skips the header for endpoints containing `budgets`.
- On 401, `apiClient` refreshes the token once and retries; a refused refresh ends the session (`sessionEnded`) and goes to `/login`. `apiClient.refreshSession()` is the only refresh path (the websocket uses it too). `apiClient.openFile` opens an authed file in a new tab.
- UI: HeroUI v3 (`@heroui/react`; compound API such as `Popover.Content`, no provider; only Popover, Tooltip and Toast are used), `@phosphor-icons/react` icons, Tailwind v4 utilities, CSS Modules (`*.module.css`, the dominant styling pattern), Recharts for charts.
- Path alias `@/` → `src/`. Import the module you use (`features/x/store/xSlice`, `features/x/components/Y`); features have no index barrels. `@/utils` is the one barrel.
- Write amounts with `utils/format.ts` (`formatCurrency`, `formatBudgetAmount`, `formatAmount`, …), never a local `Intl.NumberFormat`.
- Explicit TypeScript interfaces; `strict` is on.

## Navigation
- `/` sends a signed-in user to `/dashboard` (`HomeRoute`); `Layout` shows `AppLoader` until the first budgets load.
- The top `Navbar` (`src/components/layout/Navbar/Navbar.tsx`, `NAV_ITEMS`) is the only nav chrome. Its bell (`features/jobs/components/ReviewBell`) lists `needs_review` messages from `GET /messages`, reloaded after websocket job updates; each opens `/settings?section=jobs&job=<reportJobId>`, which Jobs finds and opens. It holds daily destinations only: Home (`/dashboard`), Transactions, Budget, Accounts, Payees, Reports.
- Occasional or configuration screens are Settings sections at `/settings?section=<id>`. Register new ones in `SECTIONS` in `src/features/settings/components/Settings.tsx` with a `group` (account / budget / automation), a description (shown as the section header), search `keywords` and the `component` to render (lazy-load heavy ones). Set `ownHeader` if the section renders its own title, or it gets two.
- Current section ids: `general`, `sharing`, `loans` (`&account=<id>`), `recurring`, `documents`, `reconcile` (`&statement=<id>`), `mail`, `jobs`, `review`, `tags`, `ai`.
- Setup: `features/budget/components/BudgetOnboarding` creates a budget; then `Layout` shows `features/onboarding/components/OnboardingWizard` (instead of the app) until `budgets.onboarding.step` is `done`. Demo users never see it. Progress is server-side (`PATCH /onboarding`), so every step writes real data rather than wizard state. `GettingStartedChecklist` on the dashboard ticks items from real data, not from the wizard's record.
- `/transactions/:id` opens that transaction's details (fetched by `transactions/normalized?id=`), and the URL follows the panel as it opens, switches and closes; link to a transaction with it. An account's list is `/accounts?account=<id>` (`Transaction` embedded with `accountId`, which leaves the URL alone); an old `/transactions/<accountId>` link redirects there.
- Legacy paths redirect to Settings: `/activity` → `section=jobs`, `/recurring` and `/review` → their sections; `/loans/:id` → `/settings?section=loans&account=<id>`.

## Gotchas
- Receipt/document bodies need auth, and `<img src>` can't send headers. Fetch with `apiClient.fetchBlobUrl('documents/<id>/content')` and use the returned object URL.
- Category goal progress is computed client-side in `src/features/category/goals/goalProgress.ts` from the month's budgeted/activity/balance. The API stores only the goal definition.
- Demo mode: `VITE_DEMO_MODE=true` shows the "Try Demo" login (needs `DEMO_MODE=true` on the API). `selectIsDemoUser` (`features/auth/store`) gates budget creation.
- `VITE_API_URL` sets the API base; the fallback in `src/config/env.ts` is `http://localhost:5151/api`.
- `features/reconcile/` is the real statement reconciliation (backed by `/api/statements`). Two views in one component: the list with upload, and one statement (`&statement=<id>`, pushed to history so Back returns to the list). Its CSS rules all carry the `.page` prefix, for the same `index.css` reset as Jobs. An import is read by a job: live progress comes from that job's websocket updates (`jobs.latest[import.jobId]`, merged by `withLiveProgress`), and statement screens reload when a `statement.*` job ends (`jobs.statementVersion`), with a 20s poll as backup. View PDF goes through `openStatementPdf` (blob fetch, since the file needs auth; the tab opens before the fetch so popup blockers allow it), shown only when `hasFile` and the file isn't a `.csv` (a bank export; uploads take PDF or CSV). "Compare with" puts the file beside the rows: `StatementPdfPanel` for a PDF (rows jump by `page`), `StatementCsvPanel` for a CSV (rows jump by `line`). `parseExport` must number records exactly as cipher's `bankexport` does (`~|~` files by line, empty lines kept; CSV by record, empty lines skipped like Go's `encoding/csv`), or the line buttons point at the wrong line. `features/statements/` (a credit card's Statements tab) renders that same `StatementReconcile` with the card's `accountId` (uploads go to the card, only its statements list); don't build a second statements UI. The list and the statement page lead with `StatementIdentity` (account or card name, last digits, period, amount due; built by `statementIdentity.ts` from the list's rows-free `summary` or the reconciliation's sections), with the file name as a detail line; a one-section statement's section header then skips the name and period. Account and category choices use the app's pickers (`AccountPicker` over `SearchSelect`, `CategoryDropdown`), not native `<select>`s. A missing row can be linked by hand to one or more "Not on statement" transactions (`LinkControls`, multi-select; a linked row still short of its amount can link more; `PUT/DELETE statements/:id/rows/:rowId/link`, stored on the row as `linkedTransactionIds` and matched before anything else); a linked pair whose amounts differ offers to book the gap as its own unapproved transaction (`POST …/difference`), linked to the row too. Several missing or EMI rows can be linked to one transaction (selection bar, or a "Not on statement" transaction's `RowPicker`; `POST statements/:id/links`); a row can be corrected (`RowEditor`, `PATCH …/rows/:rowId`). A "Not on statement" transaction can be set aside as not this statement's (`PUT …/sections/:section/aside/:transactionId`); set-aside ones fold under the table with Put back. The list groups statements by account, newest statement date first, and marks reconciled ones from `progress`; groups fold from their header, remembered in localStorage (`pennywise.reconcile.collapsedGroups`). A card section shows `CardSummary` (dues, cashback, charges, reward points, EMI plans) and a "Covered by EMI" tab; missing rows start with the API's `suggestedPayeeName`/`suggestedCategoryId` (learned from earlier statements) and take a note. The statement PDF password is set in `AccountFormModal` (write-only, `statements/passwords`). Below it sits a charges/rewards analysis that is still sample data (`features/statements/data/sampleStatement.ts`), kept outside the shared component so its `.root` element rules don't reach it.
- Lazy-load heavy routes (see `App.tsx`); settings sections are split the same way.

- Account logos: `accounts.bank` holds a logo id from `features/accounts/bankLogos.ts`; accounts without one fall back to matching the name. Credit cards render as an outlined card, other accounts as the bare logo (`BankLogo`). Loan accounts are created through `LoanAccountForm`, the rest through `AccountFormModal` (new and edit; `PATCH /accounts/:id` changes name, bank, suffix and closed, never the type). Account suffix = last digits; the API rejects one already used in the budget.
- Pickers: the generic ones (`SearchSelect`, `MultiSelectMenu`, `MiniCalendar`, `DateDropdown`, styles in `Picker.module.css`) live in `src/components/common/pickers`; each data-bound one lives with its feature (`accounts/components/AccountDropdown`, `category/components/CategoryDropdown`, `payees/components/PayeeDropdown`, `tags/components/TagFilterDropdown`). Payee/account single-select go through `SearchSelect`, dates through `MiniCalendar`, all on the common `Popover`. Don't bring back HeroUI Autocomplete/Calendar there: Calendar took 100ms+ to open, and HeroUI's layered `!important` outlines fight our CSS Modules.
- Payee rules (`features/payees`): match strings are unique per budget and the API upserts on them, so POSTing an existing string under another payee *moves* the rule. A rule with no category is skipped by cipher. `payeeUtils.testRules` mirrors the server's EXACT-then-PATTERN (ILIKE) lookup; keep the two in step.
- Dashboard figures come from `features/dashboard/store` (its own 6-month transaction window plus `reports/income-expense`), never the shared `transactions` slice: app start, budget switch, the websocket and the Transactions page reload that slice with a 30-row or filtered page. `reports/income-expense` counts opening balances as income (payee `metadata.startingBalPayeeId`); subtract them wherever "income" means earnings.
- Reports (`features/reports`): the Overview/Spending/Income/Investing tabs share one `reports/cashflow` response, classified in `cashFlow.ts`. Any transfer between an on-budget account and an asset/liability/loan account counts as invested/withdrawn/debt, never income or spending, whatever category its on-budget leg carries (users filed fund sales both to Ready to Assign and straight to categories). Group treatments (spending / one-off / saving) are guessed from the group name and overridden per device in localStorage. Loan balances come from `GET /reports/loans` (amortized server-side from `loan_metadata` and the payments booked to the loan account: each payment clears accrued interest first). Net worth and `LoanOverview` both use it; don't go back to original-minus-payments, which counts interest as principal.
- AI setup (`features/onboarding/components/AIProvidersPanel`, shown in the wizard and Settings → AI) is the user's own keys (one per provider) and the models run with them (chat or decision, one default per kind); cipher uses nothing else. Keys are write-only: omit `apiKey` in a PUT to keep the saved one. Models are tested by the server before they're saved, so a failed create is a 422 shown in the form. "Has AI" means a chat model on an enabled key (`usableModels`, `fetchHasChatModel`), not just a saved key. Provider labels live in `features/onboarding/aiProviders.ts`.
- **Server errors go through `utils/errorText.ts` before they're shown.** The API and jobs send chains like `MESSAGE_EXTRACT_FAILED: extract entities: ...`; `explainError` (title + detail) or `errorText` (one line) puts them into words, and `errorMessage` already does it for toasts. A new user-facing error code gets a line in its `KNOWN` table. The raw text stays in Jobs → technical details.
- Jobs (`features/jobs`, Settings → Jobs): the Activity tab lists every pipeline's work (emails, SMS/API messages, statements), one row per email or statement, not per job. Two client-side filters: source (`runSource`) and status. A statement upload (a tree rooted at `statement.extract`) is run kind `statement`. A day's statements fold into one row like messages do (`runGroups.sourceOf`), listing each by file name; a lone statement shows its state, file name and live progress, with its details (`statementSteps`) right under the header instead of sections. A new job type with no kind falls to `other` and shows its raw type. Updates come over the websocket (`pennywise::jobs::update`) and share one reload every 1.5s while the screen is open. Rows needing attention act from `RowActions`: Retry a dead job, Run again a stopped message (a new run replaces the stopped one, keyed by `ReceivedMessage.RunID`), Create by hand (the add-transaction form via router state, which dismisses the row once saved) and Dismiss (soft-deletes the row's jobs, keeping their idempotency keys). `jobTree.ts` turns a flat job list into chains (`buildRows`), then runs (`buildRun`) with progress; `emailGroup` decides what shows and what folds away. `runGroups.ts` folds runs into one row per source (a mailbox, SMS, API) and day, whatever became of them; a sync that's running or broke keeps its own row until it finishes. The list is split into days. Folding is off while a search or filter is on. Three days show at first and "Show older" adds three more; the load limit grows by itself until the days on screen are complete, so a group never splits. The API leaves finished syncs that found no email out of the list and its total. `index.css` resets margin and padding at one class's specificity, so Jobs CSS rules that set either need the `.page` prefix. A job with one child stays on its parent's row; a new row starts at a fork, or at a `message.received` under a mailbox job. The email's outcome comes from its `pipeline.report` label. Attempts come from `job_events` split on `claimed`, not the attempt number, because a manual retry restarts the numbers. The screen has no polling: it loads on open and on the Refresh button, until jobs get websocket events. Search and the Show filter are client-side, on what is loaded; a pasted job ID goes to the API.
- Pipelines (`features/jobs/components/PipelineView`, Jobs → Pipelines, `&view=pipeline&pipeline=<id>`): every system pipeline from `GET /pipelines` with the budget's overrides; each pipeline has its own steps, so never hardcode step IDs. Only changed fields are sent (`PUT /pipelines/:pipeline/steps/:step`, null = follow the default); `DELETE` resets a step. The server computes `effective` and `warning`; don't recompute them client-side. A PUT replaces the whole override, so every save sends `enabled` too: an `optional` step's On/Off switch saves at once with the step's other choices, and the edit form keeps the step's `enabled`.
- AI cost: money is `costMicros` (millionths of a US dollar), shown with `formatUsd`, tokens with `formatTokens`. Jobs rows show the message's cost (`RowCost`) and the open row a per-step receipt (`UsageReceipt`, from each job's `usage`); Settings → AI has `AIUsageCard` (`/ai-usage`). Agent chat shows the open conversation's cost in its header, each answer's under its last message, and each conversation's in history (`agent/conversations/:id/usage`, `usageByConversation`/`usageByRun` in the agent slice). A missing cost is "not reported", never $0.
- Review (`features/jobs/components/MessageReviewPanel`): a `needs_review` row opens on the message text and what was read from it, from the report job's `review` payload, with Continue (`POST /jobs/:id/continue`, only when `review.resume` exists), Edit and create, and Not a transaction. Show `review.text` as text, never as HTML.
- Schedules (`features/jobs/components/ScheduleView`, Jobs → Schedules, `&view=schedules`): read only, from `GET /jobs/schedules`, loaded when the tab opens. A mailbox's renewal is turned on and off by pausing or resuming the mailbox in Mail settings.
- Email sync (`features/mail/useMailConnections.ts`, used by `MailSettings` and onboarding's `EmailStep`, web only): a separate Google consent for `gmail.readonly`, independent of login. The code goes to `POST /mail-connections`; the API forwards it to ingest. It passes `prompt: 'consent'` outside the library's types, because without the consent screen Google sends no refresh token. `EmailBackfill` imports the last 30 days through `/mail-connections/:id/backfill`: every email with automatic import on, or only the ticked ones. `onboarding.emailsImportedAt` stops step 4 offering it twice; `MailSettings` offers it for any mailbox that still has access.
- Filtered total (Transactions header, shown in place of Net balance while a filter is on): `useFilteredTotals` asks `transactions/normalized` for one row with the same filters and reads the server's `totals`. Don't sum the `transactions` slice: it holds one page, and app start and the websocket reload it without filters. The search box and the mobile in/out toggle are client-side and not counted.
- Filter tray: payee, account, category and tag filters use `MultiSelectMenu` (selected pinned with Clear, then "In these results" from `useTransactionFacets` → `/transactions/facets`, then the rest). `ActiveFilterChips` under the toolbar removes one value at a time; its names come from the store by id, since the `*Names` arrays in `TransactionFilters` aren't in id order.
- Transaction time: `transactions.date` is a bare `YYYY-MM-DD`. A time of day exists only when a bank message stated one: the normalized list returns it as `occurredAt` (the first source with a time), shown beside the date in the list, the mobile cards and the detail panel through `features/transactions/utils/sourceTime.ts`, in `Asia/Kolkata` because that's the bank's clock. It's read only, and absent for a transaction made by hand: show nothing, never `createdAt`. The detail panel's "Sources" list is `GET /transactions/:id/sources` (`useTransactionSources`); `rawText` is bank text, rendered as text, never HTML. A card statement line's `rewardPoints` add up into the panel's Rewards row.
- Transaction versions: update, status, location and delete send the row's `version` from the `transactions` slice as `If-Match` (`apiClient` `ifMatch` option), and one transaction's writes run one at a time (`queueWrite`), so back-to-back autosaves don't send the same version twice. A 412 (`isVersionConflict`, from `ApiError.code`) reloads the list. A transaction that isn't in the slice saves without the check. `applyOptimisticTransaction` keeps the row's version: the edited copy may be older.
- Tag names are shown through `tagLabel` (`features/tags/utils.ts`): `<place>-<month>-<year>` names (`goa-dec-2025`) read "Goa · Dec 2025", and Settings → Tags groups them by year. The stored name never changes; search goes through `tagMatches` so both forms hit. Keep the ⓘ format help in `TagSettings` in step with `parseDatedTag`.
- Sharing (`features/sharing`, Settings → Sharing): a budget's members and invites. `budget.role` (`owner`/`editor`/`viewer`) and `memberCount` come with `GET /budgets`; a budget without a role is the user's own (`isOwner`, `canWrite`). The API enforces roles; the UI only hides what it would refuse. Only the owner sees the setup wizard, AI keys and the invite form. `PendingInvites` (invites to the signed-in user) renders nothing when there are none and sits in Sharing and on `BudgetOnboarding`, so a new user can join instead of creating a budget; accepting opens the budget (`openBudget`). Selecting a budget sends only `{ isSelected: true }`: a name in the body reads as a rename, which members can't do.
- HeroUI v3 overlay triggers: wrap a link or other element that must stay unwrapped in react-aria `Focusable` (a `Tooltip.Trigger`/`Popover.Trigger` adds a `div role="button"` around its children); use a react-aria `Button` as a popover trigger instead of nesting a `<button>`.
- Websocket (`features/websocket/WebSocketProvider`): routes each event to the slice it changes. Agent chat events (`features/agent/protocol.ts`: event names mirroring `backend/shared/model/agent.go`, stream chunk types, room ids) go to `AgentChat` through `publishAgentMessage` / `subscribeAgentMessages`.
- Toasts: use `toast` from `@/utils` (rendered and styled by `components/common/ToastHost`); give a short title plus a `description`, and use `errorMessage(err, fallback)` for failures instead of putting raw server errors in the title.
